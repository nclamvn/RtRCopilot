## Exact factory and authority-origin requirements

`db/engine.py:17–29` constructs one cached AsyncEngine, with pool 5+5 and pre-ping,
and a cached plain `async_sessionmaker(engine, expire_on_commit=False)`. It sets no
isolation, connect-time isolation settings, per-checkout isolation proof or
separate status factory. `db/uow.py:23–28` permits injected factories.

`ExecutionService.__init__` uses an injected UOW or creates one, and accepts an
independently injected ActionService. `ActionService.__init__` constructs
`ActionPolicy(self.uow)`. `ActionPolicy.current(initial_session=...)` reads from
the supplied Session instead of its own UOW factory. Therefore passing an
execution Session into an arbitrary policy would change the authority database.

The proposed trusted-origin gate must require
all of the following, decided synchronously before any Session creation or DB
work, and must fail closed to the old path:

1. `type(factory) is async_sessionmaker`, `factory.class_ is AsyncSession`,
   `type(factory.kw["bind"]) is AsyncEngine`, and exact standard asyncpg dialect
   implementation. No AsyncConnection bind, proxy/callable factory, subclass,
   alternate Session, `binds`, custom `sync_session_class` or unknown factory
   constructor options. Freeze standard options to `bind`, `autoflush=True` and
   `expire_on_commit=False`; other shapes conservatively retain legacy.
2. Execution UOW, ActionService UOW and ActionPolicy UOW must identify that same
   supported factory by object identity. Independently constructed UOW objects may
   share the exact factory, but matching DSNs must never establish authority.
3. Exact plain UnitOfWork, ActionService and ActionPolicy implementations and
   actual bound `ActionPolicy.current` method from the captured standard
   implementation, with no instance override. Custom policy/service/UOW subclass
   or replaced current method preserves the complete old path. A fake factory
   flag or broad RequestConnection shape acceptance is not a trust certificate.
4. The existing bound engine's `get_execution_options()` must expose exactly
   `{"isolation_level": "READ COMMITTED"}`. No default cache, private adapter
   flag or inferred on-connect isolation is consulted. Unknown, absent, RR,
   serializable, autocommit, extra/altered engine options route to legacy before
   DB work. The candidate does not construct or mutate an engine/options object.

These restrictions define the supported explicit-RC plain configuration; they do
not admit arbitrary custom factories. The same exact factory object establishes
execution and policy origin, not URL comparison. The public engine option is an
instruction applied on each connection construction by the supported dialect,
not a claim that a server-default observation is permanent. Arbitrary adversarial
host-code monkeypatching or changing engine event listeners/options mid-request
is outside this host-code contract, as with existing RequestConnection. Runtime
controls must bind the actual configured object and verify its instruction path.

## Why default isolation is insufficient, and explicit options are feasible

The retained SQLAlchemy asyncpg adapter source
`sqlalchemy.dialects.postgresql.asyncpg.py.txt:694–724,828–845` initializes
`isolation_level` and `_isolation_setting` to `None`, then passes that level to
asyncpg when starting a transaction. Retained
`asyncpg.transaction.py.txt:129–145` emits bare `BEGIN;` when no level is supplied;
only explicit `read_committed` adds `ISOLATION LEVEL READ COMMITTED`. Thus the
present runtime engine source does not establish a transaction-level RC override.

An engine/dialect initialization default, even if observed as READ COMMITTED in
a future read-only preflight, is one observation, not an enforceable per-generation
effective level. The retained pool reset code
`sqlalchemy.pool.base.py.txt:1399–1442` resets by rollback. It is not a general
reset/proof of committed session-level settings. Factory identity and unmodified
factory options do not certify server/user/database/session defaults for all
new pooled connections or forbid SQL-level session changes elsewhere.

The shared product factory also has ordinary unrestricted consumers. For example,
`rag/evaluation_provenance.py:57–63` starts a read transaction with a distinct
explicit REPEATABLE READ contract. That transaction-local statement is not itself
evidence of a leak into later status transactions; it demonstrates that the
shared engine is not an exclusive status lifecycle sealed by RequestConnection.

RequestConnection checks bind/session shape and task/generation authority. It
does not prove isolation. Reading private adapter fields is not an alternative
trusted lifecycle: a `None` setting is unknown, and a past field/default does not
provide the required pre-DB routing guarantee. A hidden `SHOW`, querying a server
default per request, overriding connection isolation for status or adding engine
global hooks is not authorized by the present slice.

No live isolation assertion has been made by this Builder. Default status stays
legacy, not treating retained SDK bytes as fresh runtime acceptance.

The supported explicit option follows SQLAlchemy's per-Connection
`engine_connect` characteristic setter and registers its reset callback. On
checkin the setter resets to the configured on-connect/default level. These are
SDK control calls, not a request isolation probe.
[SQLAlchemy 2.0.43 default dialect source](https://raw.githubusercontent.com/sqlalchemy/sqlalchemy/rel_2_0_43/lib/sqlalchemy/engine/default.py).
The isolation characteristic delegates to dialect setter/reset methods.
[SQLAlchemy 2.0.43 characteristic source](https://raw.githubusercontent.com/sqlalchemy/sqlalchemy/rel_2_0_43/lib/sqlalchemy/engine/characteristics.py).
Connection construction dispatches the engine-connect event before statement
execution.
[SQLAlchemy 2.0.43 connection source](https://raw.githubusercontent.com/sqlalchemy/sqlalchemy/rel_2_0_43/lib/sqlalchemy/engine/base.py).

For the retained asyncpg dialect, the setter maps `READ COMMITTED` to
`read_committed` and sets adapter state; absent an already-started transaction it
sends no SQL (`...asyncpg.py.txt:828–845,1106–1118`). The first real statement starts
asyncpg with that explicit isolation, yielding `BEGIN ISOLATION LEVEL READ
COMMITTED;` rather than a new SHOW or SET query (`asyncpg.transaction.py.txt:129–145`).
Reset after ordinary joined rollback likewise updates adapter state, without a
new transaction probe. Pre-ping and initial engine protocol remain separate from
the three application statements and must be disclosed, not hidden in counting.

Inference from that exact setter/transaction chain: an existing explicitly
configured plain asyncpg OptionEngine can enforce RC even if its server default
differs. This inference must be confirmed by a fresh finite runtime control:
outside the application query-count scope, actual SHOW isolation plus delegated
asyncpg transaction-start witness must demonstrate explicit RC. Counted status
must contain only actor projection, owner row and receipts, with the transaction
BEGIN/protocol disclosed separately. If that proof fails, STOP before further
execution; do not tune or widen the factory gate.

## Joined cleanup choice, frozen for any admitted future status candidate

Use existing `RequestConnection(factory)` plus exactly one `read_phase()` owned
by the status request task. No new connection owner, no mutation phase, no commit,
no retained carrier and no RequestConnection changes. The intended structure is:

```text
pre-DB admission gate
  → RequestConnection enter
    → one read_phase: fresh active actor → one row → ownership → bounded receipts
    → joined Session close → joined captured Connection close/checkin
  → RequestConnection exit
  → pure ExecutionView/ExecutionReceipt materialization
```

`_OwnerSession.__aexit__` joins Session close through `join_terminal`.
`phase_lease` captures the exact connection/generation and awaits `release_phase`.
`join_terminal` shields and repeatedly joins the same terminal task through
repeated cancellation, retains the original cancellation/error and clears the
terminal-task reference only after joining. `release_phase` preserves the primary
failure, poisons uncertain cleanup and clears phase handles after terminal work.
`RequestConnection.__aexit__` rejects incomplete/uncertain cleanup. There is no
successful DTO before both contexts have returned and physical checkin is proven.

No fallback after acquisition or a query failure is proposed. Only pre-DB
ineligibility routes to `_owner` then `_view` exactly as today. Error/cancellation
must propagate after joined cleanup; receipt SQL errors are not retried via the
old path. This cleanup choice is source-feasible, not runtime-tested for R14.
