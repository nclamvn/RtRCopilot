## Scope and files

Created `v2/experiments/durable_runtime/dbos_adapter.py`. It is outside serving
source/dependencies, calls the shared synthetic provider, and uses the actual
`dbos==3.2.0` workflow/step APIs. No company data or live connector is used.
The shared Builder owns Docker, dependency installation, source fixture,
manifest, trial supervisor, backup/restore and raw evidence.

The CLI preserves the engine-neutral request/output/concurrency contract.
DBOS system state is PostgreSQL when `DBOS_SYSTEM_DATABASE_URL` is configured;
the explicit fallback is actual DBOS SQLite (labelled `storage_profile`), not
a substitute implementation of DBOS. Do not mix profiles in matched results.
Stable trial-specific executor IDs permit single-executor local restart; this
does not certify automatic recovery across arbitrary dead executor IDs, HA,
Conductor, Cloud or blue/green production deployments.

## Provenance / implementation

The exact pin is `dbos==3.2.0`, verified against public pinned SDK source.
Installed wheel hashes, resolved transitive dependencies, license inventory and
vulnerability-check status belong to the shared evidence ledger. The existing
isolated fixture successfully imported this adapter on Python 3.12.4 with
installed DBOS 3.2.0 and MIT package metadata. Actual workloads and measured
results are recorded below. `raw/dev2/setup-provenance.json` retains wheel and
license hashes plus the resolved 15-package inventory. Point-in-time public OSV
queries for those exact PyPI versions reported zero advisories; this is not
OS/base-image/CLI or whole-application security certification. Isolated
SQLAlchemy 2.1.3 / psycopg 3.3.6 are not proof of serving compatibility with
SQLAlchemy 2.0.43 / psycopg 3.2.9.
[Pinned SDK source](https://github.com/dbos-inc/dbos-transact-py/tree/3.2.0),
[PyPI package](https://pypi.org/project/dbos/3.2.0/).

Actual APIs used: `@DBOS.workflow`, `@DBOS.step`, `SetWorkflowID`,
`DBOS.start_workflow`, handles, `get_workflow_status`, `list_workflow_steps`,
`set_event`, `recv`, `send`, `cancel_workflow`, `SetWorkflowTimeout`, `launch`, `destroy`.
Steps disable exception retries; interrupted steps are recovered by DBOS and
source reconciliation. Source idempotency/fencing and finite shared budgets,
not the workflow ID alone, protect external effects.

`--mode wait-prepare` reaches a real DBOS event/message wait, writes its native
checkpoint/status evidence, then holds the owner process alive for the shared
supervisor to SIGKILL. `--mode signal` launches the same executor/version,
sends an idempotent native message, then retrieves the durable result.
Current source authority is checked by `execute` after the wait, not replayed
from an earlier successful authorization step.

Optional `case.native_partial` uses the shared deterministic `partial_cases`
staging seam: first effect/receipt → real DBOS native wait → second
effect/receipt. Native cancellation while waiting must leave the first effect
and receipt intact, the second absent, and finite parent budget spent at one.
Optional `case.native_timeout_seconds` uses actual `SetWorkflowTimeout` rather
than provider scenario names. Both require observed runtime cancellation and
source snapshots before a pass can be claimed.

`--mode inspect` retains real runtime status and steps. A different running
`--version` is blocked based on DBOS's persisted `WorkflowStatus.app_version`;
the mismatched process must not produce a business receipt. Compatible recovery
must preserve the application version and workflow topology. None of these
code paths is a pass without actual execution and source/runtime state checks.

`--build compatible` selects a controlled metadata-only result implementation
with identical historical step commands, preserving the explicit application
version contract `v1`. The native compatible test starts the original code
path, SIGKILLs the owner, then resumes the compatible variant and asserts its
new result metadata. Each record contains the selected helper implementation
SHA and build identifier. This finite fixture is not arbitrary upgrade safety.

`--mode native-proofs` supervises nine raw-evidence-producing cases: compatible
code/restart, four distinct current binding mutations after native wait
(approval revision, input digest, schema digest, ACL), actual persisted version
mismatch/recovery, cancellation before effect, cancellation after partial
effect, and native timeout. It stores commands, PIDs, return codes, supervisor
SIGKILLs, runtime status/steps, source snapshots and manifest/source SHA-256.

## Issues / deviations / suggestions

- Synthetic `timeout`/`cancel_partial` statuses alone are provider/oracle
  outcomes, not proof of native runtime deadline/cancellation semantics.
  Actual native partial-effect cancellation is separately proved by r2 and
  independent native staging snapshots; source scenario names alone never
  supplied that evidence.
- Deliberately mismatched version is detected from actual runtime metadata;
  do not equate it to replay testing arbitrary incompatible source changes.
- The fallback SQLite code path is explicit but the actual measured DBOS
  branch used PostgreSQL; do not mix it with a SQLite comparison profile.
- Contractor has selected DBOS only within the verified finite local scope;
  that selection does not admit serving dependencies or authorize production.
- TIP-054.4b needs an async native wait or bounded caller/drain strategy so
  native cancellation metadata does not leave a synchronous active-future
  caller waiting for its receive body. Do not infer prompt worker termination
  from cancelled workflow metadata alone.
