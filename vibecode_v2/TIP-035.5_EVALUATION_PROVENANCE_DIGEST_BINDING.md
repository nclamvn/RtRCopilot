# TIP-035.5: Evaluation Provenance Digest Binding

## HEADER

- TIP-ID: TIP-035.5
- Project: RtR Copilot V2
- Module: Enterprise evaluation / release provenance
- Depends on: TIP-034, TIP-035.4
- Priority: P1
- Date: 13/08/2026

## CONTEXT

- Working directory: `/Users/os/RtR/KnowledgeBase/RtR_Copilot/v2`
- The direct evaluator records non-null database and ontology fields, but its
  database value is only a hash of the database name.
- The HTTP E2E evaluator currently emits `database_digest: null` and
  `ontology_digest: null`.
- The isolated E2E runner owns the exact disposable database clone and API
  container, so it is the correct trust boundary for snapshot attestation.

## TASK

Replace nullable/weak evaluation provenance with deterministic digests of the
actual active retrieval snapshot and governed runtime ontology. Bind those
digests to every HTTP E2E report before the first question is submitted, and
fail loud when provenance cannot be collected or validated.

## SPECIFICATIONS

| Requirement | Specification |
|---|---|
| REQ-035.5-01 | Compute database digest from canonical active records, active search generations and active chunks, including content/index/ACL fields used by retrieval. |
| REQ-035.5-02 | Compute ontology digest from the governed active runtime ontology, using the packaged ontology only in the existing explicit bootstrap state. |
| REQ-035.5-03 | Provide a content-free operator command inside the API image that returns build, database/ontology digests and safe row counts. |
| REQ-035.5-04 | The isolated E2E runner must collect provenance from the exact API container connected to the clone database. |
| REQ-035.5-05 | The HTTP evaluator must require valid SHA-256 digests and exact build identity; null, malformed or mismatched provenance aborts before question execution. |
| REQ-035.5-06 | Direct-mode reports must use the same real database snapshot digest rather than a database-name hash. |
| REQ-035.5-07 | Unit tests cover determinism, mutation sensitivity, report binding and fail-closed missing/malformed provenance. |
| REQ-035.5-08 | No external LLM, embeddings, reindex, connector or production operation is authorized by this TIP. |

## ACCEPTANCE CRITERIA

1. Given identical active retrieval rows, when the snapshot digest is computed
   repeatedly, then it is a stable lowercase SHA-256 value.
2. Given any relevant record, generation, chunk or ACL field changes, when the
   digest is recomputed, then it changes.
3. Given an isolated HTTP run with valid provenance, when a report is created,
   then both digest fields are non-null, valid and bound to the exact API build.
4. Given missing, malformed or build-mismatched provenance, when an HTTP
   campaign starts, then it exits before posting any question.
5. Given the current historical TIP-034 report, when it is retained, then its
   original hash remains immutable; any later attestation is stored separately
   and must not masquerade as capture-time metadata.
6. Focused tests, Ruff, mypy and `git diff --check` pass.

## CONSTRAINTS

- Do not rerun TIP-034 external capture.
- Do not mutate the original technical-capture JSON merely to replace nulls.
- Do not expose plaintext questions, answers, evidence or credentials in the
  provenance command or report metadata.
- Preserve loopback-only E2E target validation and disposable-clone isolation.
- No dependency or schema migration is required.

## DECISIONS LOG

- The fix is placed at the isolated runner/container boundary rather than a
  public web endpoint, avoiding unnecessary public metadata and ensuring the
  digest comes from the database clone actually queried.
- Historical evidence stays immutable. The debt is closed prospectively by
  code and separately attested for the already-completed capture; history is
  not rewritten.
- Blueprint checkpoint is omitted because the Homeowner explicitly requested
  closure of the documented P1 item and the design preserves existing
  architecture and security boundaries.
