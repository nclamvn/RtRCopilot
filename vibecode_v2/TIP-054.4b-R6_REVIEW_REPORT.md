## Measurement/population challenges

- The unchanged producer returns after unsuccessful admission or submission
  (latency_probe.py:73–78). Candidate OFF status/cancel50 have18 observations
  each; diagnostic ON has25 each. These are survivor populations, never100
  completed samples or implicit passes. The original criterion requires100,
  zero errors and its fixed nearest-rank p95 limit (lines87–94).
- Phase holds are emitted only on actual checkin before request closure
  (phase_profiler.py:161–181). A request with no closed hold does not prove zero
  acquisition/lease duration. Reconcile successful connect count, closed holds,
  late events, unfinished/cancelled pool intervals and request population first.
- Connect/_do_get/creation and method phases nest. Union and clip intervals at
  each request before reporting residuals. Sum only truly disjoint intervals;
  overlapping p95s are not additive. Held non-SQL is uninstrumented residual,
  not CPU, Python time or pure cleanup.
- Audit after_commit/after_rollback are client observations; after_transaction_end
  without these is end_unknown (audit_tail_observer.py:141–154). Separate all,
  known-terminal, granted and audited-COMMIT populations. An observed durable
  COMMIT with a503 response is unknown caller delivery, not rollback or success.
- PG monitor nominal50ms sampling issues activity then locks as two statements
  (pg_monitor.py:35–54); one tick is not an atomic server snapshot. Short waits,
  CPU, ping and unsampled locks remain invisible. Sample gaps and first/last
  sightings do not prove continuous duration. Match reused PIDs only inside
  the corresponding request's actual SQL time window.
- Diagnostic callbacks/monitoring have synchronous and cross-request scheduling
  costs. Serial fresh ON/OFF runs are not randomized paired counterfactuals.
  Correlation between observed contention and tails cannot select a sole cause.
