# TIP-026.9 — Utility-First Grounded Copilot

## HEADER

- TIP-ID: TIP-026.9
- Project: RtR Copilot v2
- Module: Query intelligence / retrieval / synthesis / grounding / Ask UX
- Depends on: TIP-024.7, TIP-025, TIP-026.5, TIP-026.8
- Priority: P0
- Date: 2026-08-06
- Status: Completed

## CONTEXT

RtR Copilot is an authenticated internal assistant. Its trust architecture must
prevent unauthorized disclosure and unsupported claims, but ordinary employee
questions must not be rejected merely because the corpus, a profile facet or a
requested attribute is incomplete. The current pipeline can turn completeness
into an all-or-nothing gate and therefore produce a theoretically strict but
operationally useless assistant.

This TIP makes utility the default while preserving hard security boundaries.
The policy is domain-general and must not branch on HERA or any other named
product.

## ACCEPTANCE CRITERIA

### AC-01 — Intent-graded completeness

Given an employee asks `các sản phẩm của RtR là gì?`, when the semantic planner
proposes exhaustive coverage, then the deterministic plan clamps the request to
bounded best effort because the user did not explicitly demand completeness.

Given the employee asks `liệt kê toàn bộ sản phẩm, không thiếu mục nào`, then
the plan remains exhaustive and requires a governed collection boundary.

### AC-02 — Useful partial profile

Given a profiled entity has ten configured facets but the employee is allowed
to retrieve only eight, when those eight are relevant and grounded, then the
assistant returns a grounded answer covering all eight and marks coverage
partial. It does not create a knowledge gap for the two unavailable facets.

### AC-03 — No shallow downgrade

Given all ten profile facets are available, when the answer uses only nine,
then deterministic verification repairs once and rejects if the repair remains
shallow.

### AC-04 — Security boundary

Given evidence is denied by ACL/DLP, stale under a current-only request, has an
unresolved conflict or is not cited by the final answer, then it cannot be used
or persisted regardless of utility mode.

### AC-05 — Honest coverage UX

Grounded partial answers show a neutral limitation note. Complete answers show
the normal grounded label. No inaccessible record name or authorization detail
is disclosed.

### AC-06 — Regression and live utility

Backend, integration, web and production-build gates pass. Live E2E proves a
normal HERA dossier and at least one informal/broad question returns a useful
cited answer rather than an avoidable honest-null.

## CONSTRAINTS

- Do not weaken ACL, DLP, source lineage or citation verification.
- Do not infer facts absent from authorized evidence.
- Do not expose which restricted facet or record was unavailable.
- Do not hard-code entity names or domain-specific response text in pipeline
  logic.
- A partial grounded answer is not a complete answer and must be labelled as
  such in response metadata and UI.

## DECISIONS LOG

| Decision | Rationale |
|---|---|
| Skip a new Blueprint checkpoint | The Homeowner explicitly approved the utility-first architecture in the preceding decision and ordered implementation |
| Separate enumeration intent from strict completeness | Asking for several items is not the same as demanding a certified exhaustive set |
| Enforce profile coverage only over authorized available facets | Completeness cannot become an oracle for denied data or a reason to discard useful permitted knowledge |
| Preserve explicit exhaustive gates | A user who explicitly asks for all items must not receive an unlabeled subset |
| Add response coverage metadata instead of leaking missing facet details | Gives users honest expectations without revealing restricted corpus structure |
