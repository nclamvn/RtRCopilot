# TIP-035.19 — Conversation Anchor Grounding Remediation

## Header

- Date: 15/08/2026
- Depends on: TIP-035.18 candidate `2eedb195f255`
- Trigger: build-bound TIP-034 capture, failed case `CHAT-004-T1`
- Module: grounded answer synthesis
- Priority: P0

## Context

The approved one-time TIP-034 capture passed its aggregate technical gates but
only 26/27 strict cases. `CHAT-004-T1` (`CRM bên mình làm gì?`) resolved to an
`honest_null` after 44.13 seconds with `called_answer_irrelevant`. The immutable
corpus still contains `L3F.4.001`, the ontology still binds that record to
`RtR CRM`, false-grounded count remained zero, and the next conversational turn
grounded correctly. The defect is therefore answer-shape variance after
synthesis, not missing knowledge, authorization or entity resolution.

TIP-035.13 can add a canonical subject label to a narrow class of drafts, but
an otherwise grounded provider draft may still contain an incidental foreign
entity or another shape that makes that local edit ambiguous. The current
runtime then pays for a second generation attempt and may return honest-null
despite having an approved, current, subject-bound source selected by the
provider itself.

## Requirements

- REQ-035.19-01: recover a useful answer locally when and only when a provider
  draft has already passed grounding but fails final entity relevance.
- REQ-035.19-02: recovery may use only evidence markers rendered and declared
  by that grounded draft.
- REQ-035.19-03: every recovery marker must bind to an ontology-governed
  definition/profile record for exactly one planned answer subject.
- REQ-035.19-04: recovery evidence must be approved/verified, current and free
  of entities outside the complete governed query-plan envelope.
- REQ-035.19-05: recovered prose is verbatim evidence with sentence-level
  citations; the only added text is the governed canonical presentation label.
- REQ-035.19-06: relevance, collection completeness, profile coverage, ACL,
  DLP, lineage and persistence checks remain mandatory after recovery.
- REQ-035.19-07: unsafe, unbound, exhaustive or multi-subject cases remain on
  the existing fail-closed repair path.
- REQ-035.19-08: a successful local recovery uses one generation call, avoiding
  the second-call latency/cost tail.
- REQ-035.19-09: production logic must contain no campaign ID, question string,
  CRM-specific branch or evaluator required term.
- REQ-035.19-10: BUILD and VERIFY make no external LLM/embedding call and do
  not mutate corpus, ontology, connector or runtime.

## Acceptance criteria

1. A grounded but subject-irrelevant single-entity draft is replaced by exact
   marker-selected, record-bound evidence and becomes relevant in one provider
   call.
2. Evidence not selected by the provider cannot enter the recovered answer.
3. A forged target record whose text names a foreign governed entity cannot be
   used for recovery.
4. An unbound record, stale evidence, multi-subject query or exhaustive query
   cannot use the recovery lane.
5. Existing canonical-label stabilization and foreign-entity refusal tests
   remain green.
6. The full AnswerService path persists a grounded response with the original
   citation and no second provider call.
7. Focused tests, backend regression, integration, Ruff and mypy pass locally.

## Constraints

- Do not relax `answer_relevant`, `verify_grounding` or ontology resolution.
- Do not attach a citation to generated/paraphrased factual prose.
- Do not treat record-key binding alone as sufficient when the record text
  resolves to a foreign governed entity.
- Do not reuse the failed external report as certification for a new build.
- No external recertification is authorized by this TIP.

## Decision log

- Use a bounded evidence recovery lane before the existing second generation
  attempt; it is not a permissive downgrade after timeout.
- Provider marker selection plus ontology record binding proves why a specific
  evidence block may be used. The active query-plan identity envelope prevents
  cross-entity substitution.
- Recovered output re-enters all downstream completeness and persistence gates.
- Workflow is SCAN → TIP → BUILD → VERIFY. No architecture checkpoint is
  required because API contracts and the approved trust boundary are unchanged.
