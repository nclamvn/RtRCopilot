# TIP-035.14 — Release Data Integrity & Recovery Hardening

## Header

- Date: 14/08/2026
- Depends on: TIP-035.13
- Base candidate: `cc492665a7cd00f2ed99be8d67693bf92aef901c`
- Priority: P0

## Context

The release recovery drill exposed two independent integrity defects:

1. restore verification joined every answer citation to the canonical SOT
   `chunks` table, so legitimate private-file citations were reported as 55
   broken citations;
2. the primary object metadata contained historical integration-test uploads
   whose object bytes no longer existed, while their metadata still said
   `available`.

Neither condition may be hidden or bypassed for release. The restore verifier
must understand citation provenance, and any missing physical object must be
quarantined through an explicit, audited, fail-closed operation.

## Requirements

- REQ-035.14-01: backup manifests attest the exact `file_chunks` row count.
- REQ-035.14-02: restore accepts legacy manifest v1 while requiring the new
  private-chunk attestation for manifest v2.
- REQ-035.14-03: SOT citations are verified against `chunks`; private citations
  are verified against `file_chunks` and their source/rendition checksums.
- REQ-035.14-04: runtime roles cannot update or delete private chunks after a
  restore.
- REQ-035.14-05: object reconciliation treats only an `available` metadata row
  without physical bytes as an integrity violation. Staged and terminal states
  are not false positives.
- REQ-035.14-06: marking missing objects requires both maintenance mode and an
  explicit confirmation flag.
- REQ-035.14-07: reconciliation preserves metadata, answer history and
  citations; it quarantines the object, current version, affected rendition and
  document from retrieval.
- REQ-035.14-08: the repair audit is content-free and records counts plus a
  SHA-256 digest of the affected object-key set.
- REQ-035.14-09: a fresh backup must restore into an isolated database and
  bucket with exact row counts, checksums, audit anchor and runtime controls.

## Acceptance criteria

1. The data integration suite passes the entire migration chain and the new
   maintenance-only reconciliation regression.
2. Primary reconciliation finishes with zero `database_missing` and zero
   `storage_orphans`, and the audit chain remains valid.
3. A fresh manifest-v2 archive restores successfully inside the 300-second RTO
   target.
4. Ruff, mypy, backend unit/integration and migration/image policy gates pass.
5. No production data, immutable answer record or citation is deleted.

## Constraints

- Do not infer that a missing object is disposable from its filename alone.
- Do not silently change `available` metadata during ordinary reads.
- Do not expose internal object keys in command output or audit details.
- Do not count this remediation as a new TIP-033/TIP-034 certification; those
  reports remain exact-build evidence and require a new purpose-bound approval
  after a new candidate is built.
- Production OIDC, TLS, secrets, domain and Homeowner GO remain separate gates.
## Decision log

- Reconciliation is a quarantine transition, not deletion or metadata repair.
- Retrieval remains fail-closed because the affected document/version resource
  is no longer active.
- Manifest v1 is read-compatible because its dump already includes
  `file_chunks`; only its row-count ledger lacked that table.
- Manifest v2 is the minimum format for new release backups.
