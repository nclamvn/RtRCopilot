# TIP-024.7 — Enterprise Query Intelligence & Trust Architecture

## HEADER

- **TIP-ID:** TIP-024.7
- **Project:** RtR Copilot V2
- **Module:** Enterprise ontology · query planning · retrieval · trust gates · evaluation
- **Depends on:** TIP-024.6
- **Priority:** P0
- **Approval:** Homeowner approved 2026-08-04. The target is general enterprise
  answer quality across current and future domains, never a product-specific patch.

## FOCUSED SCAN REPORT

### Existing strengths

- Immutable SOT versions, provenance, freshness, ACL-before-content retrieval,
  citation lineage, append-only audit and fail-closed grounded answering.
- Deterministic normalization plus a curated product alias table.
- External LLM query rewrite and answer generation seams with policy, DLP,
  credential, budget and circuit-breaker controls.
- TIP-024.6 question→evidence and question→answer relevance gates.

### P0 architecture gaps

1. Entity knowledge is a product-only Python dictionary, not a domain-agnostic,
   governed ontology contract.
2. Query understanding returns an augmented string rather than an immutable
   semantic plan, so downstream stages independently reinterpret the question.
3. Ambiguous, partial and colliding names have no typed resolution state.
4. LLM proposals are catalog-filtered but do not carry through retrieval and
   final verification as the same resolved entity contract.
5. The 9-case active-corpus gate is a narrow regression suite; it cannot prove
   enterprise-domain extensibility or malformed-query robustness.
6. The full canonical catalog is sent to the planner. That does not scale as the
   enterprise ontology grows.

### DECISIONS LOG

| ID | Decision | Rationale |
|---|---|---|
| D-024.7-01 | Hybrid deterministic ontology + external LLM planner | Language is probabilistic; identity, policy and verification must remain deterministic |
| D-024.7-02 | Call the planner for every eligible Ask when approved/configured | Quality is preferred over latency and cost; exact deterministic results remain authoritative |
| D-024.7-03 | Pass only a bounded candidate catalog to the LLM | Prevent catalog-size growth, prompt leakage and arbitrary entity invention |
| D-024.7-04 | One QueryPlan flows through all trust stages | Prevent semantic drift between rewrite, retrieval and verification |
| D-024.7-05 | Ambiguity fails closed in this TIP | A missing answer is safer than a confident answer to the wrong entity |
| D-024.7-06 | Externalize ontology data with digest and provenance fields | Domains can grow without modifying resolver logic and changes remain auditable |
| D-024.7-07 | No new database migration | The ontology loader is an execution contract over governed registry data; DB control-plane authoring is a later governance surface |
| D-024.7-08 | Permit external-planner expansions as a semantic relevance bridge only for open queries | Recover synonyms outside the ontology without making an LLM expansion into entity truth; original-question generation/review and deterministic grounding remain mandatory |

## VISION & BLUEPRINT

```text
raw question (stored unchanged)
  -> normalization + intent classification
  -> EnterpriseOntology candidate retrieval
       exact / approved alias / safe fuzzy / partial collision
  -> external LLM planner when approved + configured
       bounded candidate catalog; strict structured output
  -> immutable QueryPlan
       resolution state + confirmed entities + candidates + expansions + digest
  -> ambiguity gate
       resolved/open -> continue; clarification_required -> honest-null
  -> ACL-filtered hybrid retrieval using QueryPlan entities
  -> evidence relevance using the same QueryPlan entities + intent
       open query: external expansions may bridge synonyms after lexical miss
  -> quality LLM answer + independent review against the original question
  -> final relevance using the same QueryPlan entities + intent/semantic bridge
  -> grounded persistence OR honest-null + governed gap
```

### Ontology contract

The registry is data, not resolver code. Each entity has a stable id, canonical
name, type, domain, approved aliases, lifecycle, owner and provenance. Duplicate
aliases are allowed and intentionally become ambiguity candidates. The loader
validates schema, stable ids and lifecycle; its canonical JSON digest is exposed
to audit metadata without logging catalog contents.

### QueryPlan contract

The plan preserves the original question separately and contains normalized
terms, intent, confirmed entities, candidate entities, resolution state,
retrieval query, expansions, planner provenance and ontology digest. Downstream
code may consume the plan but may not reinterpret its confirmed entity set.

## ACCEPTANCE CRITERIA

1. **Domain extensibility** — Given a synthetic ontology containing product,
   policy, customer and project entities, adding a new entity requires data only
   and the same resolver links it without source-code branching.
2. **Exact and noisy input** — Canonical, spaced, case-folded, diacritic and safe
   typo variants resolve to the same stable entity id.
3. **Ambiguity** — A partial/colliding alias produces candidates and cannot call
   answer generation unless a configured planner confirms a permitted entity.
4. **Bounded planner** — The LLM sees at most the configured candidate limit and
   any output outside that set is discarded.
5. **Semantic continuity** — Retrieval, evidence relevance and answer relevance
   all use the confirmed QueryPlan entities rather than independently parsing
   the raw question; a tested external expansion may bridge non-overlapping
   synonyms for an open query but cannot override an entity decision.
6. **Unknown entity** — An unknown definition query returns no false-grounded
   evidence/answer.
7. **Live corpus** — Existing HERA/VEGA gates stay green; canonical and spaced
   OmniSight resolve to HC-013; an unresolved short form cannot silently bind.
8. **Security regression** — ACL, DLP, provider policy, budget, breaker,
   freshness, provenance and citation tests pass unchanged.
9. **Auditability** — Answer runs record plan state/counts/digests without raw
   query, alias, evidence or candidate names.
10. **Technical health** — Ruff, mypy, backend unit/integration, web, browser,
    accessibility, TypeScript and production builds pass.

## CONSTRAINTS

- Never use an LLM as the final verifier or source of entity existence.
- Never silently choose the first entity for a colliding alias.
- Never let a free-text expansion override a confirmed entity or bypass the
  original-question answer review and deterministic grounding gates.
- Never log question, evidence or catalog plaintext in query-plan audit fields.
- Never weaken policy gates to improve answer rate.
- Preserve compatibility for existing product-alias imports while making the
  ontology registry the authority.
