## CONTEXT

TIP-026.6 restored useful grounded answers for representative single-turn
questions, but the quality proof is still split across mocked browser tests,
isolated integration tests and manual live probes. The 77-turn enterprise
campaign is not yet a repeatable HTTP/browser release gate. The Ask service
also persists conversation history without using a bounded history window to
resolve pronouns and ellipsis, and a transient answer-provider failure can
consume the grounding-repair retry and double perceived latency.

The Homeowner authorized pipeline consolidation, cleanup and comprehensive E2E
coverage. This TIP extends the approved trust architecture; it does not loosen
ACL, DLP, provenance, citation, lineage or honest-null rules.

## IMPLEMENTATION DESIGN

1. Read a small recent conversation window in the same ownership transaction
   that appends the new user message. Inspect it against external-processing
   policy before it can reach the planner.
2. Extend the query-plan contract with a bounded self-contained question. The
   planner may resolve references only against ontology candidates surfaced by
   the current question plus authorized history. Retrieval ranking contains the
   original question and the resolved question; evidence and grounding remain
   mandatory.
3. Separate provider transport failure from grounding repair. A second provider
   call is allowed only after a deterministic grounding rejection.
4. Upgrade the operational campaign runner to support the real HTTP/session
   path and stable conversation IDs while retaining sanitized output.
5. Add an isolated stack runner and a separate Playwright live configuration so
   mocked component tests remain fast and deterministic.

## ACCEPTANCE CRITERIA

### AC-01 — Conversation continuity

Given a user asks about an entity and follows with a pronoun or ellipsis, when
the second turn is planned, then retrieval and synthesis use the resolved
self-contained question and return the expected governed evidence.

### AC-02 — Conversation isolation

Given a conversation belongs to another subject, when a user references it,
then the request fails as not found before history is read or sent externally.

### AC-03 — Context policy

Given recent history triggers DLP/external-processing denial, when a follow-up
is asked, then raw history is excluded from external planning and cannot appear
in provider input or response metadata.

### AC-04 — Retry semantics

Given a provider timeout/network error, one provider call occurs and the answer
fails safely. Given a grounding rejection, exactly one bounded repair call may
occur.

### AC-05 — Isolated HTTP campaign

Given the active local corpus, when the enterprise E2E command runs, then it
uses an exact `rtr_e2e_` clone and isolated Redis DB, verifies the source row
counts are unchanged, and removes only those exact temporary resources.

### AC-06 — Comprehensive semantic matrix

Given the versioned campaign, when all cases run through HTTP, then every turn
is scored for expected state, citation group, required terms, false-grounding,
latency and domain/shape stratification.

### AC-07 — Live browser journeys

Given the isolated HTTP stack, when Playwright runs, then the UI submits and
renders a colloquial grounded answer, a contextual follow-up, a full governed
collection and an unknown-entity honest-null with evidence/gap behavior intact.

### AC-08 — Full regression

`make verify`, the normal mocked Playwright suite and the isolated E2E campaign
pass with zero critical/serious accessibility findings and zero authorization
leaks.

## CONSTRAINTS

- Do not special-case RtR product names in pipeline code.
- Do not treat conversation prose or LLM output as enterprise truth.
- Do not weaken citation, current-lineage, collection-coverage or policy gates.
- Do not put credentials, raw answers or sensitive excerpts into committed
  reports.
- Do not delete or rewrite existing local audit/history records.

## DECISIONS LOG

| Decision | Rationale |
|---|---|
| Reuse the approved TIP-026 trust architecture without a new Blueprint checkpoint | The Homeowner explicitly authorized pipeline completion; changes close documented P0 gaps rather than introduce a new product architecture |
| Keep fast mocked browser tests and add a separate live suite | Deterministic UI feedback and true end-to-end evidence serve different purposes |
| Use a disposable database clone and isolated Redis DB | Ask is append-only/audited; realistic E2E must never pollute the normal local corpus or conversation ledger |
| Permit one repair call only for grounding failure | A second identical call after network/provider failure increases latency and cost without improving truth quality |
