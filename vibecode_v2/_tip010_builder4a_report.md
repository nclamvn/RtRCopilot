- D2 — TIP-003 has NO write API for bindings; per handoff I exposed the minimal binding operations the policy engine already supports internally: assign/unassign of EXISTING roles (seeded `roles` table) and EXISTING groups (`groups` table, matched on the target subject's issuer) via direct `subject_roles`/`subject_groups` writes + `subjects.security_version` bump — the same rows and bump `PostgresSubjectRepository.mutate_authority` writes, but scoped to one binding instead of wholesale replacement. No policy primitives can be created (unknown role/group keys are typed 422). CAVEAT the Contractor must know: OIDC login (`upsert_from_claims`) re-syncs roles/groups from IdP claims, so an admin-assigned role/group binding holds until the subject's next login — inherent to TIP-003's IdP-authoritative model, not new behavior. Durable admin-granted authority would be `entitlements` (untouched, out of my slice). Session projection: Postgres bump is canonical + in-transaction; `SessionStore.revoke_all` projection to Redis is best-effort after commit (logged on failure) — strictly stronger than the existing `mutate_authority`, which projects nothing.
- D3 — Gap priority mutation added (`set_gap_priority` repo+service+endpoint) per Builder 2's explicit pointer ("add a new audited repository+service method — do not widen `transition_gap`"); gated curator-or-admin like other gap mutations, 404-before-403, frozen on closed gaps.
- D4 — AC-11 "attempts produce typed errors + audit entries" is implemented as an explicit boundary tarpit: the truth families exist as admin routes that always refuse (typed 403 + audit). Field-level smuggling attempts on legitimate endpoints die as typed 422 `validation_error` (Pydantic `extra="forbid"`) BEFORE any handler — those are not DB-audited (nothing was reachable), which I judged correct: the audited event is an attempt on a truth family, the 422 is a malformed request. The unit surface-inventory test additionally pins the whole admin route set so no mutation route can appear silently.
- D5 — One-line-in-spirit fix to Builder 2's `test_queues_compute_live_membership_with_thresholds_and_scoping`: the curator freshness assertion read only the first `queue_page` (default limit 25) and started failing on the accumulated dirty DB (54 freshness members persist across runs; the expiring fixture fell off page 1). No production code or other assertion touched; the failure was data-volume flakiness, not a behavior change (it reproduces on this DB with my changes fully reverted).
