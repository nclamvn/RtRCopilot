# TIP-054.4b-R13 — Execution checkout optimization design

2026-10-09 · P1 · Vibecode Kit v6.2 · Contractor design.
Scope approved by Homeowner: focus on execution/checkout design; do not enable
the executor or advance to TIP-054.5. This document authorizes **no implementation,

## Decision

Choose **status-only read-phase fusion** as the first proposed implementation.
Remove one duplicate execution-row SELECT and two unnecessary checkout cycles
from a successful owner status request. Leave create/submit, mutation, audit,
worker, publication and output disclosure unchanged. This is a small reversible
change proposal, not a redesign of the two-lease execution architecture.

Source-derived target: **4 application SQL statements / 3 checkout holds →
3 statements / 1 checkout**. No candidate code exists and no performance benefit
has been measured. A smaller query count does not establish SLA readiness or the
sole cause of the current tail failures.

## Compare no more than three designs

| Option | Mechanism | Disposition |
|---|---|---|
| A: status read-phase fusion | Fresh current actor + one owner-checked row + existing bounded receipts, within one fresh read Session | **Choose first**; no writes or audit changes |
| B: successful INSERT RETURNING | Read immediate compatibility fields from actually inserted execution; retain fresh SELECT on conflict | Defer; new submit target 22→21 SQL, still two leases/three phases; mutation-sensitive |
| C: action-local audit-fence proof | Avoid second client acquisition only when exact same live root transaction already holds 827004 | Defer; create 29→28 / submit 22→21 SQL; wider proof/cleanup surface |

Do not remove the first audit fence, fresh authority after blocking waits, fresh
audit-chain head read, database append validation or atomic audit commit. A boolean
or `session.info` flag is not proof of a live transaction-scoped lock. Option B
must not turn conflict adoption into UPDATE/reset/replay: PostgreSQL RETURNING
contains actually inserted/updated rows, not an unchanged DO NOTHING conflict row.
[PostgreSQL 16 INSERT](https://www.postgresql.org/docs/16/sql-insert.html).

## Proposed status path

```text
Fresh task-local read Session; acquire physical checkout
  → project current persisted actor using existing initial_session seam
  → SELECT execution row once
  → compare actor ownership; deny before receipts on mismatch
  → SELECT existing bounded receipt metadata
  → await transaction/Session close and physical checkin
  → materialize the unchanged ExecutionView / ExecutionReceipt response
```

Use `ActionPolicy.current(subject, initial_session=session)`; no cached Subject
projection from an earlier request/phase. Read `_row` once, preserve active-actor
failure and missing/foreign-run 404 behavior. Only an authorized owner reaches
the receipts query. Preserve its exact fields, joins, ordering and LIMIT 100.
The DTO builder is pure and runs after awaited terminal cleanup.

A narrowly private status routine should own its Session end-to-end. Reuse the
existing receipt query and pure response projection; do not expose arbitrary
caller-supplied rows as authorization. Leave `_owner` and `_view` semantics intact
for cancel/resume/output/submit/internal runner paths. Choose the cleanup mechanism
during implementation review: retain proven joined cancellation semantics; do not
introduce a second connection owner or broad RequestConnection rewrite merely to
save two checkouts. A cleanup fault must not produce a successful response.

### Isolation and observation boundary

The first optimized path is admissible only for a factory whose effective
**READ COMMITTED** isolation is proved before runtime acceptance. Current engine
source does not set isolation explicitly; this design has not queried a live
server. PostgreSQL READ COMMITTED gives each statement a new snapshot; REPEATABLE
READ can pin a transaction snapshot at its first statement. Same Session therefore
does **not** imply equivalent freshness under every injected factory.
[PostgreSQL 16 isolation](https://www.postgresql.org/docs/16/transaction-iso.html).

Future implementation must explicitly scope the optimized seam to the supported,
verified factory. Unknown/custom/repeatable-read/serializable factories preserve
the existing status path through routing decided before DB work. Do not change
global engine isolation, infer it from a dialect name, downgrade an injected
factory or add hidden per-request SHOW/extra probes while claiming three SQL.
If a reliable narrow admission mechanism cannot be established, stop implementation
and revise the design instead of silently widening the support premise.

Bind both the execution UOW and the injected ActionService/ActionPolicy authority
origin. `ExecutionService` accepts a separately injected `actions` service; its
policy can therefore own a different UOW/factory. Passing the execution Session
to that policy would change where identity is projected. Mismatched/custom
authority origins must use the legacy path before DB work; do not infer equivalence
from a matching DSN or silently substitute one authority database for another.

The row is observed at its single SELECT, not at response delivery. A cancel
committed before that statement must be visible; one committed after it may not
be reflected in that response. Receipts remain a separate statement, as today:
this is neither an atomic row/receipt snapshot nor a latest-at-return guarantee.
The old extra view-row observation is deliberately removed. Future compatibility
review must accept this explicit metadata observation contract; otherwise retain
the second read and abandon the three-query target. Do not sell this as identical
interleaving behavior or reuse a pre-checkout row.

One continuous hold can be longer than each of the previous three short holds.
Fewer acquisitions may help pool pressure, but that is unmeasured: the eventual
experiment must report hold duration and contention, not only checkout count.

## Non-negotiable invariants

1. Metadata remains available to the current active owner after source ACL revoke;
   source content/output retains its separate fresh policy checks. Do not add a
   source-disclosure gate to status or let status authorize content.
2. No business writes, audit append, mutation lock, capability dispatch or change
   to budgets/deadlines/epochs/receipts occurs in the optimized status routine.
3. Create/submit retain two physical checkouts and three fresh logical phases.
   Initial authority is never reused after waits; final disclosure reads committed
   truth independently. No Session/result/permission cache across these phases.
4. A caller timeout or final-read error after an acknowledged commit remains an
   unknown caller outcome, not evidence of rollback. Never replay/fallback after
   mutation; reconcile through durable status. Preserve existing 503 semantics.
5. Exact owner task, captured connection, transaction and terminal cleanup remain
   accountable under SQL error and repeated cancellation; no detached cleanup or
   successful DTO returned ahead of checkin. Preserve the original failure.
6. Pool 5+5, pre-ping, 0.9s operation timeout, quotas, SLA thresholds, executor
   default OFF, historical evidence and TIP-054.5 block do not change.

## Future implementation and verification sequence — not authorized now

First request approval for one status-only implementation and local regressions.
Before changing the status path, resolve the factory-admission mechanism in a
short source-level addendum and obtain independent/Contractor review. This is an
open implementation prerequisite, not a solved capability in the current code.
The addendum must identify the trusted factory/engine/config lifecycle, how its
effective isolation is proven without request SQL, and why custom or overridden
sessions or mismatched policy/execution authority origins cannot enter the
optimized route. Freeze the joined-cleanup choice at this same review boundary.
If that cannot be demonstrated within
this narrow slice, retain the legacy path and stop; no engine-framework expansion.
Freeze its exact source/test inventory, then Builder authors code and controls;
an independent Reviewer checks premise and code before local execution. Main
verifies actual results. No load follows automatically from local PASS.

|---|---|

| Disclosure separation | Source revoke permits owner metadata but denies output/content; no additional policy grants or leaked fields |
| Cancellation/errors | Actual acquisition cancellation, real receipt-query SQL error, repeated cancellation during query/close; original timeout/error preserved; exact cleanup joined and pool fully returned |
| Durable outcome | Existing post-commit final-query timeout/ACK tests still prove committed ledger and nonreplay; status lookup reconciles durable outcome without dispatch |
| Unchanged write paths | Existing two-lease/three-transaction and audit-freshness controls; single-step create29/submit22 SQL unaffected; no ledger/audit/outbox mutations by status |
| Concurrency ownership | Concurrent status calls share a service, not a Session/connection; no child-task/old-handle authority if a connection owner is introduced |

These are planned scenario groups, **not executed tests or accepted runtime gates**.
Reuse existing `test_action_*` controls identified in the scan; author a finite
inventory rather than copying the project or rewriting old evidence/test epochs.

Only after local correctness PASS and a separate load approval: one bounded
candidate/reference comparison with fresh namespaces, fixed data and original
1/10/25/50 × 100 cells, pool/options/timeout/quotas and error thresholds unchanged.
Report attempted, observed, missing, timeout and HTTP-error populations separately,

Keep observer integrity distinct from product SLA; disclose experimental ordering

Rollback for a future implementation means reverting only the status slice to its
