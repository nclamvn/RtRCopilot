## Task instruction and authorization

The user approved implementing the complete AW-01 milestone, reusing suitable
existing foundations and performing end-to-end testing before handover. The
subsequent explicit decision restricts evaluation to **local/mock only**.
No external model call, internal corpus export, embeddings, reindexing,

Ordinary dependency resolution and local application/database testing belong to
the implementation. Existing Docker containers belonging to other applications
must not be changed or borrowed.

### Outcome

A neutral browser workspace supports a scoped session, text-file upload,
conversation, streamed tool activity, creation and follow-up revision of a
persisted Markdown artifact, download and reload. The runtime must not require
RtR ontology, corpus or a company email. The local fixture model is explicitly
labelled as a simulation; it validates integration, not semantic intelligence.

### Work packages

1. Harness and dependency proof: published pins, isolated in-repository Python
   environment, real local durability checks with simulated model responses.
2. Workspace backend: scoped storage, sessions, one run owner, versioned
   artifacts, idempotency, bounded execution, persisted events and cancellation.
3. Browser workspace: clean neutral UI, backend proxy, upload, transcript,
   composer, artifact preview/download, reconnect and actionable failure states.
4. Independent verification: relevant unit/integration checks, actual browser
   E2E and Codex integrated-browser inspection, followed by targeted repairs.

Contractor performs orchestration and independent verification. Separate Builder
agents own backend, frontend and harness proof. Shared HTTP contracts are agreed
directly; this does not authorize adding production multi-agent orchestration.

### Bounds and stop conditions

One primary agent, scoped deterministic file/artifact tools, no host shell,
browser automation tool or external MCP connector exposed to the model.
No default planner/reviewer model loop. No production code changes outside
the selected feature boundary without a concrete integration reason.
No new project copy or per-task Next.js distDir. Dependency environment stays
inside the repository. Before large installs/builds, free disk must exceed 10 GB.

The proposed PydanticAI/DBOS integration must be checked against **installed
published versions**, not assumed from documentation for another version. If
recovery/streaming/cancel cannot meet the contract through small adapters,
report the blocker and revise the harness choice within the approved plan.
Do not quietly replace durable execution with request-scoped asyncio tasks.

### Delivered outcome

The local UI at <http://127.0.0.1:3110/workspace> accepts a scoped browser session
without company email, creates independent workspaces, uploads text sources,
streams the typed agent/tool loop and persists versioned Markdown artifacts.
The Harbor synthetic fixture passed creation, follow-up revision, download,
reload and selection of the immutable first version, preserving Vietnamese text,
numbers and the logical motto. This is real product I/O with a scripted model,
not an autonomous semantic result.

The neutral backend lives in `v2/apps/workspace`; the page, BFF and UI are new
feature-scoped paths inside the existing Next.js application. Only two supported
loopback launcher scripts were added to the existing web package manifest.
Legacy backend manifests, old Ask, ontology and executor were not changed.
Generated `next-env.d.ts` drift was restored after development startup.

### Harness decision after proof

Keep **PydanticAI slim 2.62.0 plus native DBOS 3.2.0 durability**. The additional
Pydantic AI Harness package was unnecessary for this slice: scoped typed tools
and native recovery met the selected local contract without another framework.
No Coder, unrestricted filesystem/shell, multi-agent orchestration or fallback
stack was added. Dependencies are locked in the new package, not mass-upgraded
in the old application. Worker/application/workflow identities are separate from
the legacy executor. Native SQLite was sufficient for local proof; no unrelated
Docker service was used.

### Repairs driven by verification

- Corrected installed SDK event/result usage APIs instead of coding against a
  different documentation version.
- Checkpointed initial conversation/file inventory; recovery preserves original
  limits and deadline rather than resetting to current settings.
- Separated cancellation request from physical worker acknowledgement and kept
  publication fenced even when a model coroutine is not immediately preemptible.
- Added atomic physical-dispatch reservation inside the durable model boundary.
  Incomplete real-provider dispatches fail closed on uncertain replay rather
  than calling again blindly; simulation replay stays within the original cap.
- Bound cumulative provisional/final/artifact output, deduplicated persisted
  events and retained artifact receipts/version checks across process failure.
- Disabled the Workspace page/BFF by default. Dedicated launchers bind loopback;
  incoming Host/Origin and backend loopback guards are additional checks, not
  substitutes for deployment binding.
- Recovered a lost POST acknowledgement even when the run had already completed;
  reload/reconnect does not duplicate the message or dispatch.
- Sanitized provider exceptions before durable checkpointing; credentials and
  raw request headers are not intentionally written into event/error history.

The separate reviewer did not author product runtime/UI code. It reproduced and
reviewed authorization, receipt/replay, cancellation, chunked-body and event-drain
cases. No remaining observed P0/P1 was reported **within the supported local/mock
scope**. This is not a security claim for public deployment.

### Requirements still not accepted

- Real-model source understanding, natural-language tool selection and artifact
  quality, including comparison against a direct tool-enabled agent.
- Approval pause and actual MCP/external effects; source access revocation during
  suspended runs. Forged/client-supplied authority is tested, but this does not
  prove an approval workflow that is not exposed yet.
- Office rendering, general filesystem/sandbox, skills, cross-session memory,
  organization sharing, pagination/export/delete UX and production identity.
- Sources larger than the 64,000-byte single-read cap and histories beyond the
  explicit context cap do not get silent truncation; broader document handling
  belongs to the next milestone. Upload storage accepts up to 256,000 bytes per
  file, so upload availability does not mean a larger source can be fully read.
- SQLite development storage, a single new runtime owner and loopback sessions
  do not certify enterprise scale, multi-tenant SaaS or production readiness.
- Codex integrated-browser inspection confirmed neutral UI, simulation labelling,
  session/create/submit/reload and composer clearing. Its file-chooser automation
  did not complete a source upload; native-app fallback was disallowed. Full
  source-upload E2E evidence is from Playwright against the same real local API,
  not a claim that every manual integrated-browser action succeeded.

### Reuse and compatibility

The milestone reuses the existing Next.js/React toolchain, app hosting and global
providers, API path traversal middleware, test/browser infrastructure, and selected
storage/policy/durability patterns. New ownership/event/artifact contracts are
neutral. It deliberately does not import the RtR AnswerService, DocumentOS or
ActionService as the agent loop. Existing S3/identity/retrieval service adapters
are not all integrated in AW-01. The earlier 40–50% reuse estimate was a planning
estimate for the broader foundation, not a measured amount of reused code in
this milestone.
