## Outcome contracts

1. **Recovery:** keep DBOS as the only run owner, durable event cursors and
   transactional publication receipts. Cancellation/deadline/budgets survive
   restart. Reconnection cannot create a run. Unknown external-style effect
   outcomes require reconciliation rather than an unconditional retry. Keep
   valid intermediate artifacts and distinguish cancelled from uncertain effect.
2. **Connection:** fixed local MCP fixture with one scoped read and one simulated
   outbox effect. No arbitrary URLs/commands/tools. Read permission is granted
   once per workspace and revocable; normal authorized reads need no approval.
   Descriptors and returned text never grant authority. Schema/tool identity,
   policy version, workspace, actor, run, arguments and relevant artifact/source
   versions bind effect approval. Approval is server-created, finite-lived and
   immutable; reject client `approved` flags, stale/revoked grants, tampered args
   and foreign IDs. Effect receipts have stable idempotency keys, before-dispatch
   intent and explicit uncertainty/reconciliation. Reapproval must not replay an
   already completed effect. UI shows meaningful preview and receipt.
3. **Memory:** explicit user-authored workspace entries, list/edit/delete with
   expected revision and no model auto-write. Reads resolve current live data,
   not a durable cached memory body. Deletion removes usable content and fences
   active work that already consumed it if necessary; do not promise provider
   unlearning. No restoration from serialized history or restart. Mutation,
   event and download paths enforce workspace ownership.
4. **Schedule simulation:** bounded once-only scheduled prompts, due time in a
   persisted manual clock per workspace, pause/resume/cancel and atomic claim.
   Advancing the clock is an explicit local action, not host clock manipulation.
   Repeated/concurrent ticks or restarts cannot make duplicate logical runs.
   Missed/busy/error outcomes remain visible. No recurring daemon or automatic
   effect approval; scheduled effects still need the same current permission.

### What can be used now

- **Memory:** use the sidebar to save, edit and delete explicit notes scoped to
  this workspace. `fixture:memory` reads current notes through the mock agent.
  Notes never auto-save from model guesses. Revision checks and live generation
  binding fence old consumers, including follow-ups with inherited history.
- **Connections:** grant the fixed local MCP fixture once; `fixture:mcp-read`
  needs no repeat approval. `fixture:mcp-effect` presents the exact synthetic note
  and waits for Approve/Reject on the same run. Reload preserves the request.
  Actor, arguments, policy and optional artifact revision bind the server-side
  approval. The referenced artifact is **not an attached file**; only the note
  enters the synthetic outbox. The official MCP SDK is pinned to 1.26.0.
- **Receipts and recovery:** intent is persisted before the stdio dispatch.
  Unknown outcome offers reconciliation by receipt lookup, never a blind resend.
  Native DBOS remains the sole run owner. Actual process-death proof covers
  waiting approval, an approved effect, a second crash after the receipt but
  before checkpoint, then same-run recovery with one outbox entry and receipt.
- **Schedules:** create a bounded once-only prompt, pause/resume/cancel it and
  advance the persisted manual clock. Nothing wakes at a wall-clock time.
  Concurrent/repeated ticks cannot duplicate the logical run. Fractional seconds
  work consistently through API and UI. Busy jobs require another explicit tick.

These controls extend the existing monochrome workspace rail and bottom
composer. They do not reintroduce a SOT approval process for ordinary chat,
drafts or authorized read tools. Technical verification still uses scripted
commands, not a natural-language assistant presented as production-ready.
